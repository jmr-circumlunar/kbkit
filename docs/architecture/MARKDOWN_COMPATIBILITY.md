# Markdown 与 Frontmatter 兼容策略

## 1. 总原则

- 处理普通 Markdown 文件，不要求专有数据库或编辑器 API。
- 原文是唯一正文真相源。
- 未识别语法必须原样保留；解析失败不得导致内容丢失。
- 写入采用最小字节区间修改，不能把整篇文件重新序列化后覆盖。
- 第三方编辑器可继续读取和编辑文件。

## 2. 首发支持语法（候选）

- UTF-8 文本；是否接受 BOM、LF/CRLF 混合换行需测试并冻结。
- YAML Frontmatter 的受控子集。
- ATX 标题与标题路径。
- 段落、列表、引用、表格、代码围栏。
- Obsidian wikilink：目标、别名、标题锚点和 block id。
- Embed、callout、block reference、inline tag 和 frontmatter tags。

## 3. Frontmatter 策略

原始方案提出自写极简 YAML 子集解析器，避免第三方依赖，并保留未知键。该方向可行，但必须限制语法范围。

候选首发子集：
- key: scalar；
- 单/双引号字符串；
- 布尔值、null、数字；
- 简单列表与块列表；
- 不支持的复杂 YAML 结构作为原始文本保留，不做自动规范化。

锚点、别名、标签、自定义类型、复杂多行标量、重复 key、嵌套对象的行为必须在语法规范中逐项明确。不能把“能读取常见 YAML”写成“完整支持 YAML”。

## 4. 写回规则

- 保留 BOM、换行风格、未修改字段顺序、未知键和未知语法。
- 只改被明确指定的键或字节区间。
- 未能安全解析 frontmatter 时，禁止 set_prop 自动写回。
- 重复 key 或同名标题造成歧义时，selector 必须要求更精确定位。
- 写后重新解析并执行断言；失败按事务协议处理。

## 5. 块切分与身份

必须区分：
- block_id：跨编辑尽量稳定的逻辑身份；
- locator：当前文件路径、标题路径和行区间；
- content_hash：当前块内容指纹。

候选规则优先尊重显式 block ID；无显式 ID 时用确定性生成和相邻块匹配策略，但标题修改、块移动、拆分/合并、重复标题下的身份延续必须通过样本测试后冻结。不能直接把标题路径当永久 ID。

## 6. 兼容测试样本

建立覆盖标准 Markdown、Obsidian 特有语法、畸形 frontmatter、未知扩展语法、Unicode、代码块、表格、嵌套列表、重复标题和 CRLF 的 fixture。每个写入用例需验证修改字段正确且未触碰区域字节一致。
