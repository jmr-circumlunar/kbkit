# 系统职责边界

| 对象 | 负责 | 不负责 |
|---|---|---|
| kbkit 组件研发仓库 | 源码、设计、测试、CI、发布、组件自身 Git 历史 | 存放用户实际知识内容 |
| 用户知识库目录 | Markdown、附件、库 profile、用户选择纳入版本管理的资料 | 组件源代码 |
| 第三方编辑器 | 人工预览、编辑和文件浏览 | 检索索引、事务日志、Agent API |
| kbkit Core | 领域规则、检索、写入计划、治理规则 | UI、云服务、模型推理 |
| CLI/Python/MCP | 参数和协议适配、调用应用服务 | 各自实现一套业务规则 |
| SQLite 索引 | 搜索倒排、块定位和可重建元数据 | 权威正文、不可恢复的用户事实 |
| Git 集成 | 用户知识库的版本记录与历史查询 | 日常读写的强制依赖、索引存储 |
| 模型适配器 | 用户明确配置后的重排/相关性裁剪 | 事实真伪最终裁决、默认检索必需条件 |
| 自动化任务 | 按配置执行巡检、报告、安全修复和隔离生成页更新 | 自主执行高风险改写、权威页合并或物理删除 |
| Agent Skill | 询问用户、编排初始化、配置宿主调度和解释结果 | 直接绕过应用服务修改 vault |
| Agent 宿主调度 | 保存定时任务、触发对话和请求确认 | 在 kbkit 内重复实现模型会话和用户确认 |

## 两个 Git 仓库必须分清

1. 组件研发仓库：当前 GitHub 的 jmr-circumlunar/kbkit，版本化 kbkit 自身的代码、设计和测试。
2. 用户知识库 Git 仓库：未来某个用户 vault 自己的 .git，供 gitx 可选管理 Markdown 内容。

gitx 操作对象只能是明确绑定的用户 vault；不能默认操作 kbkit 研发仓库。组件测试必须使用临时 fixture 仓库。

## 人与 Agent 的协作边界

- Agent 的写操作必须通过统一 Writer 服务。
- 人通过第三方编辑器修改文件后，kbkit 必须检测内容 hash 变化并刷新索引。
- 人机同时修改同一文件时，优先拒绝覆盖并返回差异，不做静默 last-write-wins。
- 高风险结论改写、冲突裁决、合并和物理删除只生成建议或提案，除非用户明确授权。
- 定时任务首次授权后可以直接执行安全动作和隔离生成页更新，运行记录保留来源、hash、diff 和结果，用户通过事后报告审核。
- 第三方编辑器不遵循 kbkit 锁协议，因此不能承诺它在多文件事务期间读取到全局原子快照。

## 依赖边界

- 核心运行时不得要求安装 Obsidian、编辑器插件、Git、模型或云服务。
- Git 集成在检测到 git executable 不存在时返回明确的 capability unavailable，不影响核心能力。
- MCP 传输和模型服务不得成为 Core import 时的强制依赖。
- 用户 vault 的 .kbkit 派生目录、外置索引和组件研发仓库必须物理隔离。
