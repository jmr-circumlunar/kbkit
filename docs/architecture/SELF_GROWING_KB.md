# 自成长知识库架构

## 定位

kbkit 是面向智能体的本地知识库基础设施，也是一个可审计、可恢复、可持续维护的自成长知识库体系。它持续收集变化，识别知识缺口和质量问题，形成带来源的提案，再由 Agent 与用户完成确认和写回。

自成长不是后台任意改写知识库。每一次变化都必须能够回答来源、理由、影响范围、目标状态和回滚方式。

## 四类变化来源

### 知识库自身变化

- Markdown 新建、修改、移动、重命名和删除；
- Frontmatter、块结构、wikilink、反链和目录变化；
- 索引 stale、index_dirty、journal pending 和恢复状态；
- lifecycle 到期、来源缺失、孤儿页、重复候选和结构膨胀。

### 知识库审核与校验

- 定期 lint 结果；
- provenance 完整性和来源冲突；
- schema、字段词表和状态迁移校验；
- 检索 golden set 和质量指标漂移；
- 事务、索引、备份和恢复演练结果。

### 代码和组件变化

- kbkit 自身 Git commit、版本和变更摘要；
- 需求、ADR、接口契约和测试策略的变化；
- Agent Skill、MCP schema 和代码版本不一致；
- CI 失败、依赖变化和安全修复。

代码变化只作为知识更新依据和待审核材料，不应直接写入用户 vault。Agent 将变更提炼为带 commit、文件和测试证据的 proposal。

### 会话和外部工作记录

- 用户与 Agent 的当天会话摘要；
- 已确认的决策、未完成事项、纠错和反复询问；
- Agent 执行结果、失败原因和用户反馈；
- 用户明确授权接入的任务、项目和外部来源。

原始会话不自动进入知识库。系统先保存本地受控的 session artifact，再由确定性抽取和模型辅助生成候选事实，等待审核和写回。

## 自成长循环

```text
采集变化 → 规范化 → 差异扫描 → 质量检查 → 候选事实/问题
       → 证据合并 → proposal → Agent 审核/用户确认
       → dry-run diff → 事务写入 → 局部索引 → 质量复核
       → 记录结果与下一次扫描游标
```

每个阶段都可单独重跑。扫描游标、输入 hash、proposal、写入事务和复核结果必须可追溯。

## 自动化任务分层

### 每次运行都可执行的确定性任务

- 检测文件变化并增量索引；
- 检查 stale、index_dirty、pending journal 和备份状态；
- 执行 lint、schema、字段词表和链接检查；
- 读取 Git status、commit、ADR、测试和 CI 结果；
- 汇总当日 session artifact 的数量、hash 和来源；
- 生成日报和待处理 proposal 列表。

### 周期运行的模型辅助任务

- 从会话和代码变更中提取候选事实；
- 合并重复知识并给出冲突说明；
- 生成摘要、标签、provenance 和复核日期建议；
- 对检索失败样本提出缺口和改进建议；
- 生成低风险整理的 dry-run diff；用户开启 generated-content 模式后，可以直接写入隔离的生成目录。

模型服务不可用时，任务仍完成确定性扫描并保留原始证据。模型不得绕过 proposal 和事务协议直接写入正文。

### 需要用户确认的任务

- 修改现有权威页、批量移动、归档和删除；
- 冲突事实的裁决；
- 会话记录进入知识库；
- 代码变更提炼为长期知识；
- 启用外部模型或允许发送正文片段；
- 调整扫描范围、保留期限、生成目录和自动化频率。

### 定时任务的直接执行策略

定时任务在首次配置时询问授权范围，之后按照已保存的策略直接执行例行维护。直接执行范围包括增量索引、报告、事务恢复、确定性元数据修复、备份以及隔离目录中的新生成页。每次动作都留下来源、输入 hash、前后 hash、diff、任务运行号和结果，供用户事后查看。

现有权威页的事实改写、冲突裁决、合并、移动、归档和删除不属于直接执行范围。它们仍进入 proposal 或 Agent 对话流程。这样用户不需要审核每一次正常维护，又能保留对高影响知识变化的控制。

## 调度模型

Agent 宿主的定时任务优先负责需要上下文和用户交互的工作。kbkit 自带 runner 负责无宿主、离线和确定性维护。

推荐默认频率：

| 任务 | 默认频率 | 执行者 |
|---|---:|---|
| 文件差异、增量索引、事务恢复检查 | 每次 Agent 会话开始或结束 | Agent / runner |
| lint、链接、stale 和备份报告 | 每日 | Agent 宿主优先 |
| 会话摘要和代码变更提案 | 每日或用户触发 | Agent 宿主 |
| 重复、过期和知识结构整理 | 每周 | Agent 宿主 |
| golden set、质量和性能评估 | 每次版本或每周 | CI / Agent |

用户也可以通过 Skill 随时触发同一流程。手动触发和定时触发必须使用相同的任务定义、游标、proposal 和审计记录。

## 安全和可控性

- 默认只扫描用户明确授权的 vault、代码仓库和会话目录。
- 默认不读取其他 Agent 会话、密钥、环境变量和未授权路径。
- 原始会话和代码内容先落在受控 artifact 区，不直接混入正文。
- 每条候选知识必须带来源、时间、提取方式和置信度。
- proposal 风险等级由 finding 严重度映射，high 风险必须经过用户确认。
- proposal 具备 pending、approved、rejected、applied、expired、conflicted 状态。
- 任何自动写入都必须可回滚，且不覆盖用户并发修改。
- 自动化失败必须可见，不得把失败写成成功或删除原始证据。

## 长期运行的收敛规则

- 同一规则、来源和 payload 的 pending/approved proposal 只保留一个开放项，payload 使用规范化 JSON 比较；
- 维护扫描发现原 finding 已消失时，将对应 pending proposal 标记为 `expired`，不自动删除审计记录；
- 同一 vault 的维护任务使用互斥锁串行执行，避免 Agent 宿主、手动 Skill 和离线 runner 并发改写索引与状态；
- 报告同时记录总块数、变化块数、当前 findings、过期 proposal 和剩余 pending proposal，便于观察是否持续收敛。

## 项目启动影响

自成长能力改变了实现顺序。E3 最小核心必须包含扫描游标、事件记录、proposal 数据模型和可审计任务运行记录。模型辅助、复杂治理和自动整理仍可后置，但数据契约不能后置，否则后续无法可靠接入会话和代码来源。
