# kbkit — 初始化底座与目录构筑

> 姊妹篇：[[90-独立项目/kbkit-通用知识库管理组件/00-总述|00-总述]] · [[90-独立项目/kbkit-通用知识库管理组件/01-重点拆分与逐点思考|重点拆分与逐点思考]]
> 详细版：`C:\workspace\kbkit\docs\FOCUS.md`（重点零）

## 一、为什么初始化是「底座」

初始化不是「建几个文件夹」——它是**底座**。目录范式一旦定错，内容长了以后只能大规模迁移重构（等于重写一遍知识）。
所以它**优先级不是最高，但错误代价最高**，必须单列为重点。

## 二、初始化向导八步

| 步 | 输入 | 默认 / 建议来源 |
|---|---|---|
| 1 | **库目录绝对路径**（必填） | 探测：md 数 / frontmatter 比例 / wikilink 密度 / `.git` / `.obsidian` |
| 2 | **库名 + 方向描述**（选填） | 未提供 → 通用骨架，并提示「填方向可细化」 |
| 3 | 目录范式 | 依方向给 2–3 候选 + 各自代价，用户选定或自选 |
| 4 | 领域清单 | 从方向描述抽取建议主题（3–8 个）；**确认后才预建目录**，其余按需生长 |
| 5 | 字段规范 | type/kind/state/tags/source/owner/review_by/confidence/visibility 的键名 + **受控词表** |
| 6 | 运行时区 | inbox / 提案箱 / 报告区 / 排除区（默认不检索） |
| 7 | 版本与自动化 | git init + 首提交 + 快照保留期 + 是否装计划任务 |
| 8 | **底座体检** | 建索引 → 跑 lint → 输出体检报告 + 三条下一步建议 |

## 三、「方向确认」机制（最高杠杆的一次性输入）

| 要点 | 做法 |
|---|---|
| 不做零信息初始化 | 不填方向 → 通用骨架，但明确告知可细化 |
| 建议要可解释 | 每个建议附「依据你的描述建议 X，因为 Y」，不做黑箱建目录 |
| 建议要可撤销 | 初始化产物进 `.kbkit/` 快照，可一键回退 |
| 不预建空目录 | 先给清单 → 确认 → 只为确认的主题建目录 |
| **方向要沉淀** | 写入 `00-索引/库定位.md`，供后续 Agent 理解「这个库能回答什么、不能回答什么」 |

## 四、目录范式对照（2026 实践）

| 范式 | 结构 | 适合 | 代价 |
|---|---|---|---|
| PARA | Projects/Areas/Resources/Archives | 按行动性组织 | Resources 易成垃圾场；跨领域难归属 |
| 领域主题目录 | 按知识领域分层 | 主题稳定、长期沉淀 | 主题边界随时间漂移，需定期重整 |
| Johnny Decimal | 00–99 十域 × 每域十类 × 编号条目，**每文件恰一地址** | 要求地址稳定 | 三级封顶；不表达领域关系 |
| Zettelkasten + MOC | 原子笔记 + MOC 枢纽，靠链接导航 | 关系密集型 | 起步成本高，需维护 MOC |
| **混合骨架（默认）** | 编号分层顶层 + 领域目录 + MOC 导航 + inbox/triage | **自成长知识库** | 需明确「运行时产物 vs 知识内容」分界 |

> 2026 实践共识：**明确挑一种，不要半夜发明第五种**。

### 推荐默认骨架

```
00-索引/     库定位 · 领域索引(MOC) · 词表 · 规范 · 体检报告
10-主题/     领域目录（按方向确认结果建，按需生长）
20-方法/     程序性记忆区：可复用方法、工作流、模板
30-运行时/   inbox(捕获) · 提案箱 · 巡检报告 · 日志（默认不检索）
90-归档/     冻结与历史（默认不检索）
99-资产/     模板与附件
```

**关键**：把「知识内容」与「运行时产物」**在物理目录上分开** → 默认排除区成为目录级事实（不靠配置维持）。
这正是当前 AI员工知识库在付成本的地方（`01-工作台` 与知识内容混层，排除规则靠 profile + 规则双重维护）。

## 五、自成长知识库对目录的七条硬要求

| # | 要求 | 反例会怎样 |
|---|---|---|
| D1 | 运行时产物有固定去处 | 日志/提案散落 → 污染检索、库显乱 |
| D2 | 草稿与定稿分离 | 半成品被检索并被引用 |
| D3 | 活跃与历史清晰分界 | 过期内容进默认候选 → 自信地给旧答案 |
| D4 | 跨领域用链接而非搬家 | 一主题只能一处 → 重复或无处安放 |
| D5 | 新增领域不改顶层 | 顶层重构 → 全库路径变动、链接全断 |
| D6 | 能容纳程序性记忆 | 方法/工作流无处沉淀 → 重复劳动 |
| D7 | 导航层独立于内容层 | 索引页混在主题里 → 内容一动导航就烂 |

##### 补一条：排除区必须支持白名单（`exclude.allow`）

目录分区必然遇到「整体不该被检索，但里面有一两块必须可检」的情况（归档区里保留的权威结论、独立项目区里组件自己写的设计笔记、运行时区被引用的模板）。只有「整段排除」时，用户与 Agent 只能二选一：**要么放错地方，要么放弃排除规则**。

> **实测证据（2026-11-17）**：kbkit 自己的设计笔记放在 `90-独立项目/`（默认排除区），建索引后检索「三态 / journal / 故障注入」的块数为 **0** —— **组件自己写的设计文档，组件自己检索不到**。
> 因此 profile 的 `exclude` 必须支持 `allow`（子路径白名单），且 `doctor` 要检查「被引用的笔记是否落在排除区且未加白名单」。

## 六、演进能力

- 范式写在 profile → 可改；改目录要同时改链接 → **迁移脚本 + git 保底 + 链接改写**。
- 但迁移不是常规操作：设计上让「新增领域」**永不需要改顶层**（D5）。
- 目录形态参考 2026 的技术库实践：**强类型字段 + inbox 捕获 + 定期 triage + MOC/反链导航**（而非深树）。

## 七、引用验证机制（设计自身的纪律）

> 用户要求：所有引用信息需要验证，或做验证计划。

| 等级 | 含义 | 处理 |
|---|---|---|
| **V1 一手已核** | 官方文档/官方仓库，已逐字核对 | 可直接作依据 |
| **V2 实测已验** | 本机可复现的基准（本文压测数据） | 可作性能依据 |
| **V3 二手待核** | 社区文章/二手综述，未回溯一手 | **不得单独支撑关键决策**，列入待验证清单 |

**纪律**：关键决策不得只靠 V3；只有 V3 时必须在文档标注风险与替代方案，并把验证项挂到某个里程碑前。

### 待验证计划（节选）

| # | 待验证项 | 方法 | 判定标准 | 时机 |
|---|---|---|---|---|
| V1 | 本地 reranker 对中文技术文档的实际增益 | `llama-server --embedding --pooling rank` + bge-reranker-v2-m3 对同一 golden set 重排 | Hit@5/MRR 相对纯 BM25 提升 ≥10%，否则默认不启用 | M3 前 |
| V2 | 2026 技术库方案（PARA+MOC+typed properties+inbox triage）本地试跑 | 用当前 AI员工知识库做影子试跑（不动现有库） | 哪些分区值得固化、哪些是过度设计 | M1 前 |
| V3 | Copilot Memory 的过期/pinning 实际行为 | 查官方文档与 changelog | 确认有无 pinning → 写进 TTL/pinning 设计 | M4 前 |
| V4 | 冲突三模式可实现性 | 影子库构造跨源冲突样本 | 三种判别策略都有可测行为 | M4 前 |
| V5 | 深树 vs MOC 导航在千篇规模的影响 | 影子库 A/B 测 Hit@K | 差异显著则 MOC 导航定为默认 | M1 前 |
| V6 | bigram 与 reranker 的分工边界 | 同 golden set 对比 BM25 / BM25+rerank / 仅 rerank | 找到「召回 N 超过多少时模型介入才划算」的阈值 | M3 前 |
