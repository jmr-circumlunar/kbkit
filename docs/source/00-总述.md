# kbkit — 通用个人知识库管理组件（总述）

> **一句话定位**：给「一堆 markdown 文件」配一套**能检索、能维护、能版本化**的基础设施，
> 让任何 AI Agent / 任何工具在 200ms 内定位到「**哪一段话**」，而不是「哪个文件」。
>
> **它不是** Obsidian 替代品、不是编辑器、不是知识库 SaaS。
> **它是** 知识库的**检索层 + 维护层 + 版本层**，对上层（Obsidian / MCP / Skill / 人）无侵入。

## 一、为什么做（问题陈述）

现有方案的三个结构性问题：

| 问题      | 现状                                    | 后果                                        |
| ------- | ------------------------------------- | ----------------------------------------- |
| 检索单元错位  | 索引只到**标题+摘要**级，检索单元是「文件」              | 查一个字段要扫多个 md；MCP 裸搜时日记霸榜（实测一次返回 23.9 万字符） |
| 读取上下文爆炸 | 整篇 `vault_read` > 30KB 即爆（最大笔记 574KB） | 只能反复试探性读取                                 |
| 强依赖特定宿主 | 检索必须经 Obsidian MCP                    | Obsidian 不运行就没有检索；换库就得重写规则                |

**核心判断**：不必把索引做厚（那等于把全文塞进上下文），而要把**检索单元从「文件」下沉到「块」**。
索引做厚 = 把全文搬进上下文；块级索引 = 只搬**定位信息**，命中后回源取那一段。

## 二、架构（分层）

**四层：视图层 / 接口层 / 引擎层 / 存储层。视图层全部可选且都不是依赖。**

```
① 视图层（可互换 · 全部可选 · 都不是依赖）
   Obsidian / VSCode / Typora / 任意编辑器  ← 只读查看与手工编辑
   kbkit 自带本地 Web 查看器（零依赖 http.server + 单页）
        │ 直接读同一批 md 文件（无插件、无 API）
② 接口层（谁在调用）
   CLI(kbc) · MCP Server · Python API(kbkit.core) · zipapp 单文件分发
        ↓
③ 引擎层 kbkit.core（纯标准库 · 全部自持）
   storage(读写/事务) · indexer · search · graph(双链图谱) · lint · gitx
   mdio(md解析) · writer(原子写) · tasks(定时) · templates(模板) · registry(多库)
        ↓
④ 存储层：用户目录（任意结构）
   note.md（正文）+ 可选 .kbkit/（索引/快照/日志，均可删除重建）
```

**关键设计**：

- ① 与 ③ 之间**没有 API 依赖**，只有文件依赖 → 卸载 Obsidian 不影响任何能力。
- ③ 的子模块可单独使用（Python API 逐个 import），也可整体经 CLI/MCP 使用。
- ④ 的 `.kbkit/` 是**派生数据**，删除后 `index build` 完全恢复 → 数据可搬运。

##### 独立性判据（一票否决，任一不过即整体不合格）

| #   | 判据         | 验收方式                                       |
| --- | ---------- | ------------------------------------------ |
| I1  | 不依赖任何宿主软件  | 不装 Obsidian/插件/MCP，功能全可用                   |
| I2  | 不依赖网络      | 断网下 init→index→search→write→lint→commit 全通 |
| I3  | 零第三方依赖     | 干净 Python 环境 pip list 无新增包                 |
| I4  | 数据可搬运      | 复制库目录到新路径 → 重建索引 → 结果 hash 一致              |
| I5  | 格式通用       | 纯 md + 通用 frontmatter，Obsidian 打开即用但不打开也能用 |
| I6  | 分发即用       | 单文件 `kbkit.pyz` 或 pip 包，解压即上手              |
| I7  | Agent 能力完整 | 读写/检索/图谱/治理/版本全经组件 API，无需旁路工具              |

> I4 的三条验收（断网新建编辑 → 重启内容仍在 → 复制数据目录到另一台机器能还原）
> 是主流本地笔记工具的共同做法，kbkit 把它固化为自动验收脚本。

## 三、关键选型（全部有实测支撑）

| 决策点    | 选择                          | 理由                                 | 实测                     |
| ------ | --------------------------- | ---------------------------------- | ---------------------- |
| 倒排引擎   | SQLite FTS5                 | 零依赖、标准库自带                          | 万级达标                   |
| 中文分词   | 应用层 bigram + unicode61      | FTS5 官方明确 unicode61 不切中文，须应用层分词后写入 | 中文检索可用                 |
| 标识符    | `tokenchars '_'` 整体成 token  | 表名/字段名查询必须精确                       | `BAS_ACCOUNT` 精确命中     |
| 正文存储   | **不入库，回源读**                 | 索引与内容永不冲突                          | 体积 344→241MB（**−30%**） |
| FTS5 列 | 只留 title+tok                | path/breadcrumb/kind 每块重复建倒排，纯浪费   | 同上                     |
| 索引位置   | 外置 `%APPDATA%`              | 库内会拖慢 Obsidian 索引 + 污染 git         | —                      |
| 变更判定   | mtime+size / git / sha1 三件套 | git 太重做不了高频增量；mtime 会被 touch 误判    | 增量 1.05s               |
| 写入路径   | MCP 优先，组件写入需显式              | 2026-11-02 写入污染事故的教训               | —                      |

> **不选 trigram tokenizer**：官方限制「查询少于 3 个字符不匹配」，中文双字词直接废。
> **不选 jieba**：违反零依赖原则（可用 `--backend` 扩展点预留）。

## 四、性能基线（2026-11-17 实测）

**万级压测**：10,000 篇合成中文 md / 102.1 MB（含 frontmatter、表格、标识符）

| 指标        | 实测                     | 目标       |
| --------- | ---------------------- | -------- |
| 分块数       | 95,765 块               | —        |
| 全量建索引     | **31.7 s**             | ≤ 60 s   |
| 索引体积      | **240.8 MB**（原文 2.36×） | ≤ 2.5×   |
| 增量（改 1 篇） | **1.05 s**             | ≤ 2 s    |
| 查询·标识符    | **145 ms**             | ≤ 500 ms |
| 查询·高频词    | 345–376 ms             | ≤ 500 ms |
| 命中输出体积    | ~2.9 KB / 10 条         | 可控       |

**真实库**（AI员工知识库 688 篇 / 10.8 MB）：建索引 7.4s · 9,475 块 · 索引 34.6 MB · 增量 < 1s。

## 五、维护体系（借鉴主流做法）

**三层维护模型**（源自 Karpathy LLM Wiki：File Watcher / Periodic Lint / Startup Health Check）：

| 层 | 动作 | 触发 |
|---|---|---|
| 实时 | 写入后单文件重索引 | 写操作后 |
| 周期 | 健康巡检 + 增量重建 + 自动提交 | 计划任务 |
| 启动 | doctor 自检 | 会话开始 |

**健康巡检 12 条规则**（L1 断链 / L2 孤儿页 / L3 未登记 / L4 frontmatter 缺字段 / L5 标签越界 /
L6 超长页 / L7 标题层级跳跃 / L8 陈旧内容 / L9 疑似重复 / L10 计数过期 / L11 空章节 / L12 与代码冲突）。

**风险分级**（源自 Rost Glukhov 的风险分层维护）：

| 级别 | 范围 | 默认策略 |
|---|---|---|
| 低风险 | 补链、格式、计数刷新、补默认字段 | 可自动修复 |
| 中风险 | 合并重复、拆分长页、改状态 | 需显式开关 |
| 高风险 | 删断言、重写权威页、改结论 | **永不自动**，只出建议+diff |

**Git 集成**：`init/bind/status/commit/snapshot/log`；自动提交由**脚本层**执行
（不让 Agent 自行 `git add/commit`，上层权限常禁止且不稳定 —— 本项目已踩坑）。

## 六、对外接口

##### 模型可选接入（检索侧）

**不配模型 → 正常检索；配了模型 → 由模型判断「哪部分与需求相关」。**

| 档位 | 条件 | 模型动作 |
|---|---|---|
| L0 纯检索 | 未配置模型 | 无（BM25 + 符号 + 字段过滤 + 规则重排） |
| L1 重排 | 配模型 且 N ≤ 5 | 相关性打分 → 重排/截断 |
| L2 相关性裁剪 | 配模型 且 N > 10 | 判相关/不相关 → 抽取段内相关子句 → 精排（附淘汰项与原因） |

组件**零依赖**：只通过 OpenAI 兼容 HTTP 调用户自备服务（如 `llama-server --embedding --pooling rank` → `/v1/rerank`），不装模型、不带 SDK、不破坏断网可用；模型不可用则回退 L0 并显式标注 `model_stage: skipped`。

##### 初始化是底座（重点零）

八步向导：库目录 → 库名与**方向描述** → 目录范式 → 领域清单 → 字段规范与词表 → 运行时区 → 版本与自动化 → **底座体检报告**。
方向是可选输入：提供则据此**建议**领域清单/范式/词表/导航骨架并**经用户确认后落盘**；不提供则按通用混合骨架（编号分层 + 领域目录 + MOC 导航 + 运行时区物理分区 + 归档区）。

组件是**完整工具套件**，不是「给某个宿主的检索插件」。Agent 侧能力全部自持。

| 形态 | 内容 |
| --- | --- |
| CLI | `init/add/use/current/doctor/profile` · `index build/status/stats/reindex/reset` · `search/read/outline/list/find/facet/graph` · `new/set/append/edit/move/rename/rm/bulk/verify/diff` · `lint/fix/template` · `git/task` · `serve-mcp/export/version` |
| MCP Server | Agent 全量：搜索/读/标题树/清单 · **写**（统一 op 模型）· 结构变更 · 图谱 · 巡检 · git · 索引状态。工具 ≤ 8 个、参数 schema 单一真相源、错误结构化带可执行 hint |
| Python API | `from kbkit import Vault, Index, Search, Writer, Graph, Lint` 逐模块可编程调用 |
| **视图层** | **完全外包给第三方**：Obsidian / VSCode / Typora / 任意编辑器直接打开同一批 md。组件**不提供**任何渲染层，只保证「第三方能正常显示」+「Agent 能读能写」 |
| Skill | `kb-onboard`（首次使用）· `kb-query`（检索规范）· `kb-author`（写作规范） |
| 分发 | **主**：pip 包 / 一键安装脚本；**次**：zipapp 单文件 `kbkit.pyz`（Windows 需 python3.dll 在 PATH） |

##### 写入引擎（独立性的核心，组件自己负责把库写好）

针对「MCP 写入经常参数错误」这一现实痛点，七条对策：参数单一真相源 · 强制预检 · 错误可执行 · 幂等键 · 意图级高层 API · 事务与回滚 · 选择器歧义即停。

**统一 op 模型**：`create / set_prop / append / edit / move / rename / delete / bulk`，配**结构化选择器**（标题路径数组 / block id / 行区间 / 属性键），默认 dry-run 出 diff。

**事务流程**：校验 → 幂等检查 → 定位预检 → 影响面 → diff → 冲突检测（sha1）→ 【dry-run 出口】→ 快照 → 原子写（临时文件→fsync→replace→**fsync 目录**）→ 写后校验 → 事务日志 → 局部重索引 → 可选提交；任一步失败自动回滚。

##### 模块化拆分（更新能力不牵一发动全身）

36 个模块分 9 层，单向依赖，插件点隔离。**变更影响矩阵**给出量化答案：
**只有 7 个模块（M01/M05/M07/M09/M13/M14/M15）改动需要重建索引，其余零索引影响。**

##### 格式兼容（兼容 ≠ 依赖）

读写通用子集并**原样保留**未识别语法：frontmatter/Properties、wikilink（含别名/标题/块 id）、embed、callout、block ref、`#tag`、标题层级。
自写极简 YAML 子集解析器（零依赖）；解析不了的键保留原文不丢；写回只改被显式修改的行，其余字节不动。

## 十、写入一致性与可丢性（重点九 · P0）

**单文件原子写不够**：POSIX `rename` 只保证单文件原子替换，不延伸到多文件；而 Agent 改一次知识库往往跨多个文件（改条目 + 改状态 + 改 manifest + 改引用）。

**协议：write-ahead + image-based redo**

```
预检(三态定位 + sha1 冲突) → 计划(after-image) → 快照
  → 先落 journal 与 staging（fsync）→ 逐文件 os.replace → 局部重索引 → 收尾
```

- **日志存「修改后完整内容」而非操作意图** → 恢复只需把内容写到位，天然幂等、可校验、可人工审阅
- **只前滚不回滚** → 回滚会毁掉用户在这期间的合法修改；前滚只在「仍是旧镜像」时才动它
- **三态恢复**：`applied` 跳过 / `pending` 前滚补写 / `divergent`（有人改过）**绝不自动覆盖**，保留 journal 报冲突待人工判断
- **四道防漂移**：定点最小改 · 三态定位（歧义绝不取第一个）· 写前 sha1 乐观锁 · 写后断言；第五道：结论型内容与既有 active 断言冲突时**转提案**
- **索引失败不牵连内容** → 索引是派生数据可重建，内容是真相源不可再生；索引失败只标 `index_dirty`
- **可靠性契约**：「写入后的错误不能证明回滚已经发生」→ 错误诚实区分 `rolled_back` / `partially_applied` / `unknown`
- **必须有故障注入验证**：7 个注入点 kill 进程 → 恢复后断言「全旧或全新、无半截文件、链接不断、索引一致」

依据（2026）：Konnect 原子写入与多文件事务（日志先于改动落盘、三态恢复、只前滚、可靠性契约）· MemoryCustodian v0.12.0（2026-10，Agent 改持久记忆跨多文件需事务化）· Atomic Store / fs-transaction（staged change sets + all-or-nothing apply + write-ahead recovery）。
