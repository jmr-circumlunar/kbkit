## 一、重点总览（十项 · 含重点零与重点九）

| # | 重点 | 本质问题 | 优先级 |
|---|---|---|---|
| **零** | **初始化与目录构筑（底座）** | 库的结构一次定错，后面全是重构 —— 底座要稳且能演进 | **底座级**（含在 M1） |
| 一 | **查询 / 检索引擎建设** | 让 Agent 用最少调用找到最准的那一段，且知道它可能不完整 | P0 |
| 二 | **维护（写入 + 索引同步）** | 让变更安全、即时、可回滚，内容与索引永不脱节 | P0 |
| 三 | **自动化维护（自成长）** | 知识库不依赖用户维护：自己发现问题、能修的修、不能修的升级 | P1 |
| 四 | **膨胀与过期治理** | 让内容严谨有效且精简：增长受控、过期可控、冗余不积压 | P0 |
| 五 | **版本管理** | 让每次变更可追溯可回滚；让「为什么这样写」不随人消失 | P1 |
| ★ 六 | **溯源与可验证性** | 每条知识能回答「从哪来、谁负责、何时复核、可信度多少」 | P0 |
| ★ 七 | **质量度量与评测闭环** | 让「检索好不好」可度量、可回归，而不是靠感觉 | P1 |
| ★ 八 | **生命周期、权限与恢复** | 让知识有状态与分级，事故可恢复，人机共写不打架 | P1 |
| ★ 九 | **写入一致性与可丢性** | 写多文件时不漂移、不丢、不留半成品 —— 横跨写入/索引/版本三层 | **P0** |

> **用户给的五点**为骨干（查询 / 维护 / 自动化 / 防膨胀过期 / 版本管理），**补五项**：重点零（初始化底座）+ ★ 六/七/八/九。
> **重点零单列**的理由：优先级不是最高，但**错误代价最高** —— 目录范式定错 = 全库重构。
> **重点九单列**的理由：横跨写入 / 索引 / 版本三层，只属任何一层都解决不了 —— 多文件统一更新必须事务化。
> 详见 [[90-独立项目/kbkit-通用知识库管理组件/02-初始化底座与目录构筑|初始化底座与目录构筑]]。

## 二、依赖顺序（实施顺序不是随意排的）

```
重点六 溯源与状态字段 ──┐
                        ├─▶ 重点四 膨胀与过期治理 ─┐
重点二 写入+索引同步 ──┘                            ├─▶ 重点三 自动化维护
                                                  │   （自成长需要度量判据）
重点九 写入一致性/事务 ──（横切，贯穿重点二/四/三与索引）
                                                  │
重点一 查询（状态过滤+stale+溯源）──▶ 重点七 质量度量 ┘
                                                  │
                                                  ▼
                                            重点五 版本管理（贯穿全程）
```

> **关键结论 1**：**查询不是第一优先，溯源 + 状态 + 写入一致性才是。**
> 库本身失真时，检索引擎再强也只是更快地返回错误。
>
> **关键结论 2**：**重点九不是某一层的附属，而是横切保证** —— 它横跨写入（内容）、索引（派生）、版本（留痕）三层，
> 任何一层单独做都保证不了「不漂移、不丢」。所以它必须在重点二开工时同步落地，而不是后期补。

## 三、逐点核心判断（各 3–6 条，详见 FOCUS.md）

##### 重点九 · 写入一致性与可丢性（横切写入/索引/版本三层）

1. **要防四类失败**：漂移（写的不是想写的）· 覆盖（用户手改被盖）· 半成品（批量写一半失败）· 崩溃（断电留半截）。
2. **单文件原子写不够** —— POSIX `rename` 只保证单文件原子替换，不延伸到多文件；一次 Agent 写库操作往往跨多个文件（改条目 + 改状态 + 改 manifest + 改引用），必须事务化。
3. **协议：write-ahead + image-based redo** —— 预检(三态定位+sha1 冲突) → 计划(after-image) → 快照 → **先落 journal 与 staging（fsync）** → 逐文件 `os.replace` → 局部重索引 → 收尾。
4. **日志存「修改后完整内容」而非操作意图** —— 恢复只需把内容写到位，天然幂等、可逐文件校验、可人工审阅。
5. **只前滚，不回滚** —— 回滚会把用户在这期间的合法改动也毁掉；前滚只在「仍是旧镜像」时才动它。
6. **三态恢复**：`applied` 跳过 / `pending` 前滚补写 / `divergent`（有人改过）**绝不自动覆盖**，保留 journal 报冲突待人工判断。
7. **四道防漂移**：定点最小改 · 三态定位（歧义绝不取第一个）· 写前 sha1 乐观锁 · 写后断言（实际 == after-image）；第五道语义护栏：结论型内容与既有 active 断言冲突时**转提案而非直接写**。
8. **索引失败不牵连内容** —— 索引是派生数据可重建，内容是真相源不可再生；索引失败只标 `index_dirty`，**绝不连带回滚正确内容**。
9. **可靠性契约**：「写入后的错误不能证明回滚已经发生」→ 错误必须诚实区分 `rolled_back` / `partially_applied` / `unknown`。
10. **必须有故障注入验证**：7 个注入点（staging 半途 / journal 写完未改 / replace 到第 N 个 / 索引更新中 / git 提交前 / 并发写 / 事务中途被改）kill 进程 → 恢复后断言「库内容全旧或全新、无半截文件、链接不断、索引一致」。

##### 重点一补充 · 模型可选介入（L0/L1/L2）

> 用户设想已落地：**不配模型 → 正常检索；配了模型 → 由模型判断「哪部分与需求相关」**。

| 档位 | 条件 | 模型动作 | 输出标记 |
|---|---|---|---|
| L0 纯检索 | 未配置模型 | 无 | `model_stage: none` |
| L1 重排 | 配模型 且 N ≤ 5 | 相关性打分 → 重排/截断 | `model_stage: rerank` + 每条 `model_score` |
| L2 相关性裁剪 | 配模型 且 N > 10 | 判相关/不相关 → 抽取段内相关子句 → 精排 | `model_stage: judge+extract` + `rejected[]`（淘汰项与原因） |

- **组件零依赖**：只通过 OpenAI 兼容 HTTP 调用户自备服务（`llama-server --embedding --pooling rank` → `/v1/rerank`）；不装模型、不带 SDK、不破坏断网可用（本地服务优先）。
- **降级必须显式**：模型超时/不可用 → 回退 L0 + 标注 `model_stage: skipped`，不静默。
- **收益要用数据说话**：先用 golden set 对比（验证项 V6），提升不显著则默认不启用 L2 —— 不为「有模型」而用模型。
- **修正上一版判断**：查询改写「该不该由组件做」取决于有没有模型 —— 未配模型时组件只给建议，配了模型才可受控改写（可关闭 + 标注 `query_rewritten`）。

##### 重点零 · 初始化与目录构筑（底座）
1. **初始化最大的风险不是「建得不够」，而是「建得过多 + 建错了不可改」** → 默认最小骨架；主题目录先给清单、确认后才建、后续按需生长。
2. **「方向」是最高杠杆的一次性输入** → 决定领域清单/范式/词表/导航骨架，且必须写进库（`00-索引/库定位.md`），供 Agent 理解「这个库能回答什么」。
3. **范式要明确挑一种，不要发明第五种**（2026 实践共识）；kbkit 提供五种预设 + 代价说明 + 默认混合骨架，但不提供自由画树。
4. **运行时产物必须物理分区** —— 这是自成长库与普通笔记库最大的结构差异；否则默认排除区只能靠配置维持（我们当前正在付这个成本）。
5. **演进能力内建**：范式在 profile 里可改，迁移需脚本 + git 保底 + 链接改写；但目标是「新增领域永不需要改顶层」。
6. **底座验收 = 体检报告**，不是「目录建好了」：索引可建、lint 可跑、词表生效、导航齐全、git 首提交完成、计划任务已装。

### 重点一 · 查询
1. **2026 的「Hybrid 默认」不能照抄** —— 那些结论的前提是有 embedding 服务与重排模型；kbkit 零依赖断网可用 → 默认只能 BM25 + 符号 + 字段过滤。技术文档里「唯一符号」天然零噪声。
2. **Agent 场景下查询改写不该由组件做** —— Agent 自己就是 LLM，天然会把模糊意图翻译成精确条件；组件只给「改写建议」，由 Agent 决定是否采纳。
3. **真正杠杆在上下文打包，不在 top-k** —— Agent 一个任务会发几十个小查询，且 top-k 向量检索在该规模会失效；组件要做的是「字段过滤 + 分面收敛 + 按预算打包刚好够用的片段」。
4. **重排用规则不用模型** —— 标题命中 / 新鲜度 / 路径深度 / 块型 / 符号精确加权，全部可复现可解释。
5. **可信标记必须进结果契约** —— 库改了索引没刷新时必须标 `stale`，否则 Agent 会自信地漏答。

### 重点二 · 维护（写入 + 索引同步）
1. **同步粒度是「文件」** —— 实测增量 1.05s（万级），可做到写完立刻同步 → 即时一致性，这是自成长闭环的前提。
2. **写入必须顺带维护元数据** —— 文件 + 链接图谱 + frontmatter + 索引四者一致；写后校验四件套：frontmatter 完整 / 标题树非空 / 链接可解析 / 索引已同步，任一不过即回滚。
3. **一致性要可判定** —— `built_at` vs 库内最新 mtime → 结果标 stale。
4. **冲突检测不可省** —— 写前比对 sha1，人机同改时拒绝并给差异。
5. **删除默认进回收站** —— Agent 误删是常态，物理删除不可逆。

### 重点三 · 自动化（自成长）
1. **前提是度量先落地** —— 没度量就没「变好还是变坏」，自愈即盲动。
2. **动作分级** —— 低风险自动修 / 中风险出提案 / 高风险只报告 + diff。drift 是数据卫生问题，不是模型问题 → 治理手段必须是数据层的确定性规则。
3. **提案箱是自动化的「人机接口」** —— 不能自决的事写成带期限与责任人的条目，超期升级。
4. **经验沉淀必须回链原文** —— 纯事实抽取会丢细节；沉淀标注「提炼非原文」，否则库会被二手概括填满、越用越失真。
5. **过期用 TTL + pinning 双机制** —— 2026 的 Copilot Memory 默认 28 天过期且**没有 pinning**（社区批评），单一 TTL 不实用。
6. **禁止自动物理删除** —— 过期 = 标记失效 + 移出默认检索。

### 重点四 · 膨胀与过期治理
1. **膨胀三源** —— 重复产生 / 过期留存 / 二手概括堆积，要对症下药，不能只靠「定期清理」。
2. **不用物理删除当主要手段** —— 用 `state` 控制「默认可检索集合」，物理内容仍可追溯。
3. **去重必须用确定性算法** —— simhash/熵出候选，LLM 只裁决「谁更权威」；更便宜、更快、更确定。
4. **「新」不等于「对」** —— 权威性看来源与责任人，不看 updated；跨源分歧 → 两方都保留 + 标注 contested + 查询时按需解决。**禁止静默覆盖。**
5. **增长要有硬预算** —— 总量/主题/单页/自动生成占比；超预算转提案箱而非硬拦。
6. **「精简」要可度量** —— 有效率、过期率、冗余率、平均存活期；**曲线比绝对值重要**。

### 重点五 · 版本管理
1. **git 是版本层不是知识层** —— 没有 git 也能正常用，git 是可选增强。
2. **自动提交按日聚合 + 固定前缀** —— 「回到昨天」一次 checkout；空变更不提交；提交在脚本层。
3. **索引/快照绝不进 git** —— 实证：某站把搜索索引每 5 分钟提交进 git，仓库被撑到 639MB。
4. **把「决策」当一等公民版本化** —— 规范类/结论类笔记须记录「为什么」与「否决了什么」，理由进版本库。

### ★ 六 溯源与可验证性
1. **「答案可追溯到来源」是默认能力** —— 2026 多个同向实践：带引用的知识图谱、上下文链路 insight→quote→source→raw、治理化 markdown（owner/review date/provenance）。
2. **断言与实体分离** —— provenance 附在**断言与重要关系**上，不只是节点。
3. **提炼必须回链原文** —— 结构化链接，而非模糊的「来源：某次会话」。
4. **owner 是治理落地角色** —— profile 可配「目录/领域 → 责任人」，巡检查「无主知识」。

### ★ 七 质量度量与评测闭环
1. **检索层与生成层分开评** —— RAGAS 的 Context Recall 属生成层视角，不能替代检索层独立评估。
2. **golden set + CI 门禁是防回归唯一可靠手段** —— chunking/tokenize 是高频改动点。
3. **真实反馈最被低估** —— wrong-answer mine：每周抽样真实问答 → 判正确/部分/错误 → 回溯到文档 → 更新/废弃/合并。
4. **三档评分优于 1–10** —— fully met / partially met / not met 更易审计。

### ★ 八 生命周期、权限与恢复
1. **状态机是防膨胀的结构手段** —— draft → active → review_due → deprecated → archived，合法迁移由组件约束。
2. **`state` 必须驱动检索默认行为** —— 默认只返 active，这就是「逻辑瘦身」的落点。
3. **敏感分级** —— private/internal/public；默认检索过滤；个人库同样有账号、薪酬、客户数据。
4. **备份要有可还原性测试** —— 没验证过的备份等于没有。
5. **人机共写冲突给三方合并视角** —— 基线/用户/Agent 三版差异，而不是二选一。
