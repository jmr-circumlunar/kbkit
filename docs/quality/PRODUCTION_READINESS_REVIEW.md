# 全量功能与架构审核

审核范围：E0–E7 当前实现、E8 本地验收证据，以及“个人长期自成长知识库”的核心目标。

## 结论

当前开发版具备 Markdown 增量索引、维护报告和提案的本地闭环。隔离生成页的自动刷新、外部来源跟踪和漏跑检测仍需实现。下文有关这些能力的描述是目标策略，现状以 [信息新鲜度与漂移处理](../architecture/KNOWLEDGE_FRESHNESS.md) 为准。

本轮修复了两个长期运行风险：

- proposal 使用规范化 JSON 去重，重复维护不会重复堆积相同 finding；
- finding 消失后，仍处于 pending 的对应 proposal 自动标记为 `expired`，避免提案箱越来越长；
- 维护任务使用 vault 级互斥锁，避免 Agent 宿主、手动命令和兜底 runner 并发更新索引或状态。

## 定时任务与准确性

定时任务按统一任务定义触发扫描和安全执行。扫描顺序固定为：增量索引 → 图与 lint → 证据汇总 → 安全修复或隔离生成 → proposal → 报告。模型不可用时仍能完成确定性步骤，模型生成内容只有在用户开启 generated-content 模式且目标为隔离生成目录时才可直接写入。

准确性由以下边界保证：

1. 只扫描用户授权的 vault、代码和会话 artifact；
2. 每条候选保留来源、输入 hash、规则或提取方式和任务运行记录；
3. 高风险变更、冲突事实、批量整理和删除必须由用户确认；
4. 写入前检查 expected hash，写入后可恢复，外部并发修改会转为冲突；
5. 手动触发、Agent 宿主触发和本地 runner 使用同一套索引、游标、proposal 和报告。

## 定时任务与精简性

精简性依赖可重复的收敛机制：相同 finding 只保留一个开放 proposal，已解决 finding 会过期，生成页使用固定目录和源 hash，重复生成更新同一 revision，权威页不会被摘要覆盖。周期间隔建议为：会话开始或结束做增量扫描，每日做 lint、备份和代码事实同步，每周做重复候选和过期知识整理。

当前实现已经覆盖 deterministic lint、链接、生命周期和 proposal 收敛。语义去重、摘要和冲突裁决仍是可选模型阶段，不能把它们当作准确性的单一保障。

## 检索证据与发布限制

Windows、Python 3.13.9、SQLite FTS5 下，100/500/1000 篇临时 Markdown 的唯一 token 查询均单命中，查询保持毫秒级，重复构建无新变化且明显更快。10,000 篇补测全量构建 53.190 秒，唯一查询 1.4 毫秒，详见 [SCALE_SEARCH_REPORT.md](SCALE_SEARCH_REPORT.md)。

发布前仍需补充：中文 bigram、标题权重、误召回 golden set、真实 Agent 宿主 Skill 加载和第三方 MCP 客户端验证。10k 构建已经实测为 53.190 秒，满足当前 60 秒门槛，但仍应继续优化到接近 31.7 秒历史基线。它们是发布证据和性能优化项，不改变当前核心闭环的设计判断。

## 最终判断

当前处于 E8 验收。公开 GitHub 默认分支仍是脚手架版本，空白 Agent 在初始化步骤受阻。开发版和公开版证据分别记录于 [功能模拟验证报告](FUNCTIONAL_SIMULATION_REPORT.md)。
