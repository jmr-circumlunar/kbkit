# 性能基线与检索质量评测

## 1. 原始设计报告的 M0 数据

以下为用户原始设计文档记录的数据，状态是“历史基线/待复现”，不是本仓库独立跑出的结果。

### 合成库

- 10,000 篇合成中文 Markdown；
- 原文约 102.1 MB；
- 95,765 个块；
- 全量建索引 31.7 秒，原目标 ≤60 秒；
- 索引 240.8 MB，原目标 ≤2.5 倍原文；
- 修改 1 篇的增量索引 1.05 秒，原目标 ≤2 秒；
- 标识符查询 145ms；
- 高频词查询 345–376ms；
- 查询目标表中写 ≤500ms；产品定位文字另写“200ms 内定位”。

### 真实库

- 688 篇、10.8 MB；
- 9,475 个块；
- 建索引 7.4 秒；
- 索引 34.6 MB；
- 增量 <1 秒。

## 2. 必须澄清的指标冲突

- “200ms 内定位”是产品定位，表格发布目标为 ≤500ms，当前高频词数据为 345–376ms。
- 两者不能混成一个通过结论。建议把 ≤500ms 作为当前发布门槛，把 ≤200ms 作为优化目标；是否采用 P50/P95、冷/热缓存和硬件归一化，需在基准规范中冻结。
- 现有报告没有完整记录 CPU、内存、磁盘、Python/SQLite 版本、缓存状态、查询集和统计分位数，必须补齐才能复现。

## 3. 基准测试规范

每次报告至少记录：
- OS build、CPU、RAM、磁盘类型；
- Python、SQLite、FTS5 版本与能力；
- 数据生成器版本、seed、文档数、字节数、块数；
- 索引 schema 版本和配置；
- 冷启动/热缓存条件；
- 查询类别、查询数量、预热轮数、P50/P95/P99；
- 索引体积、构建时间、增量时间、峰值内存；
- 与上一版本差异和原始日志。

## 4. 检索 Golden Set

至少覆盖：
- 中文双字词、短词、长词、同义表达；
- 英文、中英混合、表名/字段名/下划线标识符；
- 标题命中、正文命中、代码/表格命中；
- 状态、可见性、路径排除与白名单；
- stale 内容、过期知识、重复知识和冲突知识；
- 低频精确查询与高频泛词查询。

每条 query 标注相关块、相关等级、必须排除的块和理由。检索层独立评估，不以模型最终答案质量代替。

## 5. 指标

- Hit@K：前 K 个结果是否至少命中一个相关块。
- Recall@K：前 K 个结果覆盖多少已标注相关块。
- MRR：第一个相关结果的倒数排名均值。
- Precision@K：前 K 个结果中相关结果比例。
- Stale false-negative：索引陈旧却未标 stale 的比例。
- Exclusion leakage：被排除内容进入默认结果的比例，目标为 0。
- Context budget overflow：超过声明预算的比例，目标为 0。

阈值应先建立当前版本基线，再按真实任务设定门槛。原始资料提到 Hit@5 0.8，但其引用为二手来源，未核验前不直接作为强制门禁。
