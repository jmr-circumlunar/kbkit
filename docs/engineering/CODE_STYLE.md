# 代码规范与工程约束

状态：E1 冻结，适用于首个实现版本。

## 运行时与依赖

- 支持 Python 3.11、3.12、3.13。开发机可使用 Python 3.13.9。
- 核心运行时只使用 Python 标准库和 Python 自带的 SQLite 接口。
- Git、MCP 客户端和模型服务属于可选外部能力，不得成为核心流程的隐式依赖。
- 新增依赖必须先提交 ADR，说明体积、许可证、离线行为和对 I3 的影响。

## 包与模块

- 使用 `src/` layout。公共 API 只从 `kbkit` 和明确的公共子模块导出。
- 依赖方向为 domain → application → adapters。领域层不得导入 CLI、MCP、Git 或具体文件系统实现。
- 一个模块只负责一个稳定职责。跨层调用通过显式接口和数据对象完成。
- 不创建没有行为、测试或契约的空模块和占位类。

## Python 代码

- 遵循 PEP 8，使用 4 个空格缩进，UTF-8 编码。
- 所有公共函数、类和模块写清类型标注。公共返回值使用稳定的数据对象或结构化字典。
- 异常使用专用异常类型和稳定错误码。禁止用字符串匹配异常文本作为业务判断。
- 文件、数据库连接、锁和子进程使用上下文管理或等价的确定性释放。
- 路径统一使用 `pathlib`。用户路径必须经过根目录约束和规范化检查。
- 不在库代码中写终端输出。CLI 负责格式化应用服务返回结果。
- 日志写 stderr 或日志文件，不向 MCP stdio 的 stdout 写非协议内容。

## 数据与写入

- Markdown 原文是正文唯一真相源。索引、缓存和快照必须可标记状态并可重建。
- 写操作默认 dry-run。selector 零匹配、多匹配或歧义时必须停止。
- 修改前校验 `expected_hash`，冲突不得静默覆盖。
- 未知 Markdown 语法和未知 Frontmatter 字段必须保留。不能安全解析时拒绝属性写回。
- 持久格式、公开 API、错误码和事务语义变更必须先更新 ADR、契约和测试追踪。

## 测试与提交

- 测试验证用户可观察行为和失败语义，不以覆盖率替代正确性。
- 新功能至少包含单元测试和一个契约或集成测试。涉及文件、SQLite 或事务时必须加入临时目录测试。
- 每个缺陷修复应增加能复现原问题的测试，除非问题只能由外部系统验证并已记录证据。
- 提交信息使用 Conventional Commits。每个提交保持可构建、可测试。
- 功能使用 `feat/` 分支，缺陷使用 `fix/` 分支，文档和决策使用 `docs/` 分支。

## 评审门槛

提交合并前必须通过测试、`kbc doctor`、依赖审计和文档追踪检查。涉及平台行为时必须在 Windows 验证，并记录操作系统、Python、SQLite 和 commit SHA。
